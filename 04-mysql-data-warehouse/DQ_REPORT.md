## 二、发现的问题（按影响分级）

### P0 · 时区口径错误 → 每天 0–8 点数据错位（已修）

**现象**：第一版 DWD 只有 98,914,484 行，比预期少约 123 万。

**排查过程**：
1. 先怀疑 NULL → `SUM(ts IS NULL)` 为 0，排除
2. 再查窗口外行数 → 1,236,274 行，与差额同量级
3. 对比窗口定义：隔离区用的是**北京时间**窗口 `[1511539200, 1512316800)`，DWD 用的是 **UTC 切日** → `2017-11-25 00:00–08:00`（北京时间）这 8 小时被夹在两天之间，**两边都不落**

**修复**：
```python
CST = 8 * 3600
day_start = calendar.timegm(day.timetuple()) - CST   # 关键：减 8 小时
```

**结果**：DWD 重建后 100,095,182 行，账平。**这条坑对任何「秒级时间戳 + 北京时间业务」的数仓都适用，已写进指标口径文档。**

---

### P1 · 时间戳越界 55,576 行（已隔离，未删）

| 项 | 值 |
|---|---|
| 越界总数 | 55,576 |
| 其中负数时间戳 | 5,886（最小 −2,134,949,234） |
| 最早异常值 | 2004 年 |
| 最晚异常值 | 2033 年 |

**处置**：不删除、不改写，整行进 `dwd_dirty_rows` 并打 `reason = 'ts_out_of_window'`。

**理由**：脏数据是证据，删了就没法回溯；分析层用 DWD 时天然过滤掉。比「原地 UPDATE 成正确值」安全得多——后者的错误不可逆。

---

### P1 · 完全重复 49 行（DWD 已去重）

去重键：`(user_id, item_id, ts, behavior)`，保留 `rn = 1`。

**为什么是这四个键**：少了 `behavior`，会把「同一秒既浏览又加购」误删；少了 `ts`，会把真正的多次浏览合并，低估活跃度。

**实测代价**：只剔除 49 行，说明埋点质量很高；但规则必须留，换一份脏数据就能救命。

---

### P2 · 三类结构性限制（不可修，只能声明）

| 限制 | 后果 |
|---|---|
| 无价格 / 无订单号 | GMV、客单价、ARPU、ROI **一律算不了** |
| 无退款标记 | `buy` 只能视为成功购买，无法剔除退款 |
| 无会话 ID | 漏斗只能做**集合口径**，不能做严格路径；留存 cohort 只能按首访日 |

**这些限制已全部写入 `METRICS.md` 的「算不了的指标」清单。** 面试被问到「为什么没有 GMV」时，答案是「数据没有价格字段，我改用订单数与转化率」——比硬编一个数安全一万倍。

### P2 · 极端值（观察项，未处理）

| 项 | 值 |
|---|---|
| 用户×日行为数 最小 | 1 |
| 平均 | 14.36 |
| 最大 | **526** |

526 次/天 ≈ 每 2.7 分钟一次行为，符合「重度用户 + 脚本化浏览」的混合长尾。**没有删除**，原因：
1. 无法证明是爬虫（数据里没有任何客户端标识）
2. 删掉会破坏 UV 与 PV 的对账
3. 正确做法是分析时**分层看**（剔除 Top 0.1% 后再算均值做敏感性检验），而不是直接砍数据

## 五、这次校验带来的三条经验

1. **对账要三层闭合**：ODS = DWD + 隔离 + 剔除。只想「DWD 应该等于 ODS」会一直差一点，差一点就是一笔糊涂账。
2. **脏数据要隔离不要修**：隔离可回溯，改写不可逆。
3. **异常值分两种**：数据错误（删/隔离）与业务波动（写进结论）。把双十二当成 bug 修掉，是最典型的初级错误。
