# 电商用户行为数仓 · 指标口径文档

> 数据源：淘宝 UserBehavior 公开数据集（2017-11-25 ~ 2017-12-03，9 天，1.0015 亿条原始日志）
> 库：MySQL 26.7 `taobao_dw`　｜　分层：ODS → DWD → DWS → ADS + DIM
> 本文档解决的问题：**每个指标怎么算、边界在哪、哪些指标这份数据根本算不了。**

---

## 0. 先看这几条边界（比指标定义更重要）

| 边界 | 事实 | 影响 |
|---|---|---|
| 时间口径 | `ts` 是 Unix 秒（UTC 时基），但数据集按**北京时间**划分天 | 切日必须 `dt = date(timegm(day) - 8h)`，否则每天 00:00–08:00 的数据会错一天 |
| 无金额字段 | 5 列里没有价格、金额、订单号 | **GMV、客单价、ARPU、ROI 全部不可算**，只能算订单数、转化率、行为计数 |
| 无退款/取消标记 | `behavior` 只有 pv / fav / cart / buy 四种 | `buy` 视为成功购买，**无法剔除退款与取消** |
| 无渠道/设备/地域 | 只有 user_id、item_id、category_id | 无法做来源、设备、地区拆分；UV 只能按 `user_id` 去重 |
| 行为无顺序保证 | 同一用户同一天可能多次访问，行为之间没有会话 ID | 漏斗只能做「集合意义上的漏斗」，不能做严格路径漏斗（见 §3.5） |
| ID 为脱敏数字 | user_id / item_id / category_id 都是整数 ID | 能做规模分析，不能做真实用户画像 |

**一句话**：这份数据够做「流量、行为、转化、留存、分群」，不够做「钱」。

## 2. 去重口径（DWD 的核心规则）

同一用户、同一商品、同一秒、同一行为出现多行，视为**上游埋点重复上报**。

```sql
ROW_NUMBER() OVER (
  PARTITION BY user_id, item_id, ts, behavior
  ORDER BY ts
) AS rn
-- 只保留 rn = 1
```

**为什么是这四个键**：少了 `behavior` 会把「同一秒既浏览又加购」误判为重复；少了 `ts` 会把短时间多次浏览合并，低估活跃度。

**实测影响**：1.0009 亿行里剔除 **49 行**完全重复——重复率约 4.9e-7，说明这份数据质量相当好，但规则仍要有，否则换一份脏数据就直接翻车。

## 3. 核心指标定义

### 3.1 PV（页面浏览量）
```
PV = COUNT(*)  WHERE behavior = 'pv'
```
**口径边界**：原始行计数，不做去重、不做会话切分。同一用户刷新 10 次算 10 次。

### 3.2 UV（活跃用户数）
```
UV = COUNT(DISTINCT user_id)
```
**口径边界**：
- 本数据集**没有设备 ID**，同一自然人换设备无法合并 → UV 会被高估
- 反之同一账号多端登录会被算成 1 个 → 也可能低估真实性
- **不存在「去重 UV / 不去重 UV」的选项**，因为原始数据就没有访问日志粒度

### 3.3 人均浏览量
```
pv_per_uv = PV / UV
```
**用途**：衡量内容吸引力与粘性。**注意**：分母是 UV 不是 DAU，因为没有登录态，无法区分「访问了但没登录」。

### 3.4 购买转化率（两种口径，别混用）
```
口径 A（用户级）：buy_uv / uv          -- 有多少比例的人最终买了
口径 B（行为级）：buy 次数 / pv 次数    -- 每 100 次浏览带来几单
```
**本仓库默认用口径 A**（`dws_traffic_d.cvr_user`），因为它对业务更可解释：**「每 100 个进来的用户，19 个会下单」**。

口径 B 只在分析「内容效率」时用。两者数值差一个量级，混用会被质疑。

### 3.5 转化漏斗（集合口径，不是路径口径）
```
浏览 → 加购或收藏 → 购买
```
**必须说明的限制**：数据里没有会话 ID，无法确认「这个人先浏览、再收藏、然后买」的**顺序**。所以：

- ✅ 可以算：有多少人出现过加购行为、多少人出现过购买行为、两者交集比例
- ❌ 不能算：几人走完「浏览→加购→支付」的完整路径、在哪一步具体流失

**面试如果被追问「你这个漏斗怎么保证顺序」——正确答案是「这份数据做不到，我改用集合口径并把限制写进了文档」。** 硬编一个顺序反而是减分项。

### 3.6 复购率（三个口径，选一个并说明）
```
按用户：买过 ≥2 天的用户数 / 买过的用户数
按订单：buy 次数 ≥2 的用户数 / 买过的用户数
按商品：同用户买过 ≥2 个不同商品的用户数 / 买过的用户数
```
**本仓库用「按天」**：`buy_days >= 2`。理由：没有订单号，无法识别「同一天买两次」，只能以天为单位近似。

### 3.7 留存（cohort 口径）
```
留存 Dn = 首访日 = D 的用户中，第 D+n 天仍有行为的用户数 / 首访日 = D 的用户数
```
**口径边界**：
- cohort 按**首次出现日**划分，不是按注册日（数据里没有注册信息）
- 观察窗口只有 9 天 → 最早 cohort 最多看 D7，最晚 cohort 只能看 D0
- **双 12 预热（12-02/12-03）会把 D7 留存抬到 98.55%**，这不是 bug，是活动效应，必须写进结论

### 3.8 RFM（M 用频次替代金额）
```
R = 最后活跃日距观察期末的天数（越小越好）
F = 活跃天数
M = 购买次数（⚠️ 不是金额，因为数据无价格）
```
**分层规则**：三项各用 `NTILE(5)` 五等分打分（R 取反），按 R/F/M 高低组合映射到八段中文标签（重要价值 / 重要保持 / 重要发展 / 重要挽留 / 一般价值 / 一般保持 / 一般发展 / 一般挽留）。

**必须声明的偏差**：M 本该是金额，这里用次数替代 → **高客单低频次用户会被低估**，八段标签适合看「活跃度结构」，不适合做「消费能力分层」。

### 3.9 用户价值分层（SCD2 拉链）
```
high = 当天有 buy
mid  = 当天有 cart 或 fav，但无 buy
low  = 只有 pv
```
**为什么用拉链表**：用户价值会迁移，普通全量快照会丢失「什么时候变的」。SCD2 用 `start_dt` / `end_dt` 记录每段的生效区间，`end_dt = 9999-12-31` 表示当前有效。

**实测**：987,991 个用户产生 4,192,553 个版本段，人均 4.2 段；典型用户 9 天里在 low→mid→low→high→mid→high 之间迁移 6 次。

## 4. 这份数据算不了的指标（写进文档比硬凑更专业）

| 指标 | 为什么算不了 |
|---|---|
| GMV | 无价格字段 |
| 客单价 | 无价格、无订单号 |
| 退款率 / 退货率 | 无售后字段 |
| ROI / 投放效率 | 无花费数据 |
| ARPU / ARPPU | 无金额 |
| 新客获取成本 | 无渠道与花费 |
| 会话时长 / 跳出率 | 无会话 ID 与页面停留 |
| 严格路径漏斗 | 无会话 ID，行为无顺序 |

**如果面试官问「这份数据的价值在哪」**：价值在于**行为结构与转化效率**，不在金额——「我能说清每天多少人进来、多少人加购、多少人下单、第二天还回来多少」，这已经覆盖运营 80% 的日常判断。
